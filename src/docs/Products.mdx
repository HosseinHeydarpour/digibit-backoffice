## Use case

این صفحه **چرا و چگونه** مسیرها ساخته شده‌اند را مستند می‌کند، نه یک کامپوننت بصری — برای دیدن
جدول محصولات، storyهای `Features/Products` را باز کنید. برای دنبال‌کردن مسیرِ یک URL در
router، کامنت `TRACE` در `products.routes.ts` را بخوان.

This page documents **why and how** the routes are wired, not a visual component — for the products
table itself, open the `Features/Products` stories. To trace a URL through the router, read the
`TRACE` comment in `products.routes.ts`.

## How to use

| Route                | Page            | Real content           |
| -------------------- | --------------- | ---------------------- |
| `/products`          | `ProductList`   | list table — BO-F02    |
| `/products/new`      | `ProductCreate` | create form — BO-F07   |
| `/products/:id/edit` | `ProductEdit`   | edit form — BO-F07     |
| `/products/:id`      | `ProductDetail` | detail — later F tasks |

هر route در `products.routes.ts` اعلام شده و `loadChildren` آن را lazy می‌کند (chunk
`products-routes`). هر route `data.title` (عنوان topbar)، `data.breadcrumb` و
`data.permission: 'products.view'` را دارد.

Every route is declared in `products.routes.ts` and `loadChildren` loads it lazily (the
`products-routes` chunk). Each carries `data.title` (topbar heading), `data.breadcrumb`
and `data.permission: 'products.view'`.

## Logic

حرف اول `new` پیش از `:id` می‌آید تا به‌عنوان یک id گرفته نشود؛ `:id/edit` دو بخش دارد و هرگز
با `:id` (یک بخش) تداخل نمی‌کند، چون شمار بخش‌ها فرق دارد. گیتینگ مجوز روی route هنوز اعمال
نمی‌شود — guard مربوطه BO-D07 است؛ `data.permission` فقط ثابتِ آماده برای آن است.

The literal `new` precedes `:id` so it is never captured as an id; `:id/edit` has two segments and
can never be shadowed by `:id`, because the segment counts differ. Route permission gating is not
enforced yet — the guard is BO-D07, and `data.permission` is only the constant it will read.

## The list page (BO-F02)

ستون‌ها در یک آرایهٔ `cols` با `field/header/width/sortable` تعریف شده‌اند و داده با signal از
`ProductsService` می‌آید، بنابراین فیلترهای BO-F03 بدون رفرش صفحه اعمال می‌شوند. خروجی fetch از
یک `state()` می‌گذرد — `error > loading > empty > data` (BO-E07) — و صفحهٔ خالی همان
`<app-empty-state>` مشترک را با دکمهٔ «افزودن محصول» نشان می‌دهد.

Columns are declared in a `cols` array carrying `field/header/width/sortable` and data arrives as a
signal from `ProductsService`, so BO-F03's filters apply without a page refresh. The fetch's outcome
goes through one `state()` — `error > loading > empty > data` (BO-E07) — and the empty shop renders
the shared `<app-empty-state>` with an «افزودن محصول» action.

## لایهٔ داده / The data layer (BO-F05)

`ProductsService` تنها نقطهٔ تماس صفحه با داده است. صفحه هیچ fixture یا `HttpClient` نمی‌شناسد؛
فقط `list/get/create/update/remove/setStatus` را صدا می‌زند. `list()` یک `Page<ProductListItem>`
برمی‌گرداند (نه آرایه) تا `total` سرور برای صفحه‌بندی BO-F04 در دسترس باشد.

`ProductsService` is the page's only data seam. The page knows no fixture and no `HttpClient`; it
calls `list/get/create/update/remove/setStatus`. `list()` returns a `Page<ProductListItem>` (not a
bare array) so the server's `total` is available to BO-F04's paginator.

### یک درخواست، مرحله‌به‌مرحله / One request, traced

ورودی:

```ts
products.list({
  query: 'سونی',
  categoryId: '3',
  page: 2,
  pageSize: 10,
  sort: 'price',
  dir: 'desc',
});
```

| گام | چه اتفاقی می‌افتد                                                                                                             |
| --- | ----------------------------------------------------------------------------------------------------------------------------- |
| ۱   | `buildQuery` فیلترها را به `query=سونی&categoryId=3&page=2&pageSize=10&sort=price&dir=desc` تبدیل می‌کند.                     |
| ۲   | `ApiService.getPage('/products', params)` درخواست `GET /api/v1/products?…` را با هدر `X-Mock: 1` می‌فرستد.                    |
| ۳   | `mockInterceptor` ماژول `products` را می‌شناسد و `filterProducts` را صدا می‌زند.                                              |
| ۴   | فیلتر متن روی `name + slug + sku`، فیلتر `categoryId` و سپس سورت قیمت نزولی اعمال می‌شود.                                     |
| ۵   | `paginate` ردیف‌های ۱۰ تا ۱۹ را برمی‌گرداند و `meta: { page: 2, pageSize: 10, total: N }` می‌دهد.                             |
| ۶   | `ApiService` پاسخ را به `{ items, total, page, pageSize }` تخت می‌کند؛ صفحه `items` را در جدول و `total` را در فوتر می‌خواند. |

`buildQuery` مقادیر `null`، `undefined`، رشتهٔ خالی و `page/pageSize` غیرمثبت را **حذف** می‌کند؛
`dir` هم فقط همراه با `sort` فرستاده می‌شود.

`buildQuery` drops `null`, `undefined`, empty strings and non-positive `page/pageSize`; `dir` only
travels with a `sort`.

### قاعده‌ها / Rules

- **مدل‌ها فقط type هستند.** `features/products/models/product.model.ts` هیچ مقدار runtime ندارد
  (همان قاعدهٔ cross-chunk در `AGENTS.md`).
- **mock داده را ذخیره نمی‌کند.** fixture آرایهٔ ثابت است؛ نوشتن واقعی در فاز REAL-API انجام
  می‌شود. این کار باعث می‌شود یک تست روی تست بعدی اثر نگذارد.
- **`isActive` حذف شد.** وضعیت محصول یک منبع حقیقت دارد: `status: 'published' | 'draft' | 'inactive'`.
- **خطا قرارداد جهانی دارد.** `ApiService` هر خطا را به `ApiError` تبدیل می‌کند؛ `get` روی id
  نامعتبر `status: 404` و پیام فارسی سرور را می‌دهد.

- **Models are types only.** `product.model.ts` carries no runtime value (the cross-chunk rule in
  `AGENTS.md`).
- **The mock does not persist.** The fixture array is frozen; real writes belong to the REAL-API
  phase, so one test cannot affect the next.
- **`isActive` is gone.** A product has one source of truth for its state:
  `status: 'published' | 'draft' | 'inactive'`.
- **Errors keep the global contract.** `ApiService` normalises every failure to `ApiError`; `get`
  with an unknown id yields `status: 404` and the server's Persian message.

## فیلترها و URL / Filters in the URL (BO-F03)

چهار فیلتر بالای جدول قرار دارند: جستجوی متنی (نام/SKU)، دسته، برند و وضعیت. وضعیت آن‌ها در
URL نگه داشته می‌شود، نه فقط در کامپوننت:

```
/products?query=سونی&category=3&brand=5&status=draft
```

The table exposes four filters: text (name/SKU), category, brand and status. Their state lives in
the URL, not only in the component:

```
/products?query=سونی&category=3&brand=5&status=draft
```

### نام‌ها / Names

| در URL     | در API       | توضیح                                                                   |
| ---------- | ------------ | ----------------------------------------------------------------------- |
| `query`    | `query`      | متن جستجو؛ `buildQuery` آن را trim می‌کند.                              |
| `category` | `categoryId` | شناسهٔ دسته؛ نگاشت در `filtersToQuery`.                                 |
| `brand`    | `brandId`    | شناسهٔ برند؛ نگاشت در `filtersToQuery`.                                 |
| `status`   | `status`     | فقط `published`/`draft`/`inactive`؛ مقدار ناشناخته نادیده گرفته می‌شود. |

The URL is the human-readable name (`category`), the API is the typed name (`categoryId`); the
mapping lives in one pure module, not in the template.

### یک تعامل، مرحله‌به‌مرحله / One interaction, traced

ورودی: کاربر در `/products` عبارت «سونی» را تایپ می‌کند و سپس دستهٔ ۳ را انتخاب می‌کند.

| گام | چه اتفاقی می‌افتد                                                                                                                 |
| --- | --------------------------------------------------------------------------------------------------------------------------------- |
| ۱   | `input` → `searchControl.valueChanges`                                                                                            |
| ۲   | `debounceTime(300)`؛ تایپ سریع فقط آخرین مقدار را نگه می‌دارد.                                                                    |
| ۳   | `applyFilters` مقدار را در `filters$` می‌گذارد و URL را با `replaceUrl` به `?query=سونی` تغییر می‌دهد.                            |
| ۴   | `combineLatest(reload$, filters$)` → `switchMap` درخواست قبلی را لغو و `list({ query: 'سونی', … })` را صدا می‌زند.                |
| ۵   | mock فیلتر را روی `name + slug + sku` اعمال می‌کند و `Page` برمی‌گرداند.                                                          |
| ۶   | `page()` به‌روز می‌شود؛ `items()` جدول و `total()` فوتر را می‌سازند.                                                              |
| ۷   | انتخاب دسته همان مسیر را با `categoryId: '3'` تکرار می‌کند؛ URL به `?query=سونی&category=3` می‌رسد.                               |
| ۸   | «پاک کردن فیلترها» هر چهار کلید را `null` می‌کند؛ `queryParamsHandling: 'merge'` پارامترهای BO-F04 (`page`/`sort`) را حفظ می‌کند. |
| ۹   | رفرش یا لینک مشترک: `route.snapshot.queryParamMap` → مقدار اولیهٔ `filters$` → اولین درخواست همان فیلترشده است.                   |
| ۱۰  | Back/Forward: اشتراک `route.queryParamMap` وضعیت را همگام می‌کند، بدون ناوبری دوباره.                                             |

The same path in English: input → 300 ms debounce → `applyFilters` writes `filters$` and the URL →
`switchMap` cancels the in-flight request and calls `list()` → the mock filters → `page()` redraws
the table. Picking a category repeats it with `categoryId`, and clearing writes four `null`s while
`merge` preserves BO-F04's `page`/`sort`.

### قاعده‌ها / Rules

- **یک منبع حقیقت برای URL.** `product-filters.ts` تنها جایی است که `query/category/brand/status`
  را می‌خواند، به API نگاشت می‌کند و به `queryParams` برمی‌گرداند. `product-filters.spec.ts`
  همهٔ این قواعد را بدون `TestBed` تست می‌کند.
- **جستجو debounce دارد، انتخاب‌ها ندارند.** تایپ ۳۰۰ms صبر می‌کند؛ select بلافاصله اعمال
  می‌شود، چون یک انتخاب عمدی است.
- **`replaceUrl` تاریخ مرورگر را شلوغ نمی‌کند.** فیلترها state موقت‌اند، نه صفحهٔ جدید.
- **خالیِ فیلترشده با فروشگاه خالی فرق دارد.** اگر فیلتری فعال باشد، پیام «محصولی با این
  فیلترها پیدا نشد» و دکمهٔ «پاک کردن فیلترها» می‌آید؛ نه «افزودن محصول».
- **گزینه‌های دسته/برند از سرویس می‌آیند.** `ProductsService.categories()`/`brands()` صفحهٔ
  lookup را می‌خوانند و گزینهٔ `isActive === false` را حذف می‌کنند؛ هیچ لیستی در کامپوننت
  hardcode نشده است.

- **One source of truth for the URL.** `product-filters.ts` is the only place that reads
  `query/category/brand/status`, maps them to the API and writes them back. Its spec covers every
  rule without a `TestBed`.
- **Search is debounced; selects are not.** Typing waits 300 ms; a select applies immediately,
  because it is one deliberate choice.
- **`replaceUrl` keeps history clean.** Filters are transient state, not a new page.
- **A filtered empty is not an empty shop.** With an active filter the copy says «محصولی با این
  فیلترها پیدا نشد» and offers «پاک کردن فیلترها», not «افزودن محصول».
- **Category/brand options come from the service.** `categories()`/`brands()` read the lookup
  endpoints and drop `isActive === false`; no list is hard-coded in the component.

## صفحه‌بندی و سورت / Paging and sort (BO-F04)

پایین جدول سه کنترل دارد: بازهٔ نمایش (مثلاً «نمایش ۲۱ تا ۴۰ از ۱۳۷ محصول»)، انتخاب
تعداد در صفحه (۱۰/۲۰/۵۰) و شماره‌های صفحه. هدرهای «نام محصول»، «قیمت» و «تاریخ ثبت»
کلیک‌پذیرند و جهت سورت را بین صعودی/نزولی عوض می‌کنند.

The footer carries the visible range, a 10/20/50 size select and the page numbers. The
name, price and createdAt headers are clickable and toggle asc/desc.

<Canvas of={ProductListStories.Paginated} />

### نام‌ها / Names

| در URL | در API     | پیش‌فرض | توضیح                                         |
| ------ | ---------- | ------- | --------------------------------------------- |
| `page` | `page`     | ۱       | ۱-based؛ `page=3` یعنی صفحهٔ سوم.             |
| `size` | `pageSize` | ۲۰      | فقط ۱۰/۲۰/۵۰؛ مقدار دیگر نادیده گرفته می‌شود. |
| `sort` | `sort`     | —       | فقط `name`/`price`/`stock`/`createdAt`.       |
| `dir`  | `dir`      | `asc`   | فقط همراه با `sort`؛ `desc` یا `asc`.         |

مقادیر پیش‌فرض از URL حذف می‌شوند: `/products` یعنی صفحهٔ ۱ با ۲۰ ردیف و بدون سورت،
نه `?page=1&size=20`. `replaceUrl` هم باعث می‌شود جابه‌جایی سریع صفحه‌ها history را
شلوغ نکند.

Defaults are omitted from the URL (`/products` means page 1, size 20, no sort) and
`replaceUrl` keeps rapid page changes out of the history.

### یک تعامل، مرحله‌به‌مرحله / One interaction, traced

ورودی: کاربر در `/products` روی صفحهٔ ۲ می‌رود، سایز را ۱۰ می‌کند و روی «قیمت» دوبار کلیک می‌کند.

| گام | چه اتفاقی می‌افتد                                                                                                                    |
| --- | ------------------------------------------------------------------------------------------------------------------------------------ |
| ۱   | `onPageChange(2)` عدد را به بازهٔ مجاز clamp می‌کند و `applyPaging({ page: 2, … })` را صدا می‌زند.                                   |
| ۲   | `writeState` یک‌بار `state$` را به‌روز و URL را با `replaceUrl` به `?page=2` تغییر می‌دهد.                                           |
| ۳   | `combineLatest(reload$, state$)` → `switchMap` درخواست قبلی را لغو و `list({ page: 2, pageSize: 20, …filters })` را صدا می‌زند.      |
| ۴   | mock ردیف‌های ۲۱–۴۰ را برمی‌گرداند؛ فوتر «۲۱ تا ۴۰ از ۱۳۷» و دکمهٔ صفحهٔ ۲ `aria-current="page"` می‌گیرد.                            |
| ۵   | انتخاب سایز ۱۰ → `onPageSizeChange` صفحه را ۱ می‌کند و `size=10` را در URL می‌نویسد؛ ۱۰ ردیف و ۱۴ صفحه.                              |
| ۶   | کلیک اول «قیمت» → `sort=price&dir=asc&page=1`؛ کلیک دوم → `dir=desc`. mock قیمت را **عددی** سورت می‌کند.                             |
| ۷   | `pageWindow` برای مجموعه‌های بلند فقط اول، آخر و صفحهٔ فعال ±۱ را نگه می‌دارد؛ در موبایل شماره‌ها با «صفحهٔ ۲ از ۷» جایگزین می‌شوند. |
| ۸   | رفرش: `pagingFromParams` از `route.snapshot` همان page/size/sort را قبل از اولین درخواست بازمی‌گرداند.                               |

The mock sorts numbers (including `createdAt` as UTC millis) before slicing, so page 2 of
a price sort is the true 21st–40th cheapest row, not a string sort of the first 40.

### قاعده‌ها / Rules

- **`product-paging.ts` تنها مترجم این چهار پارامتر است.** `pagingFromParams` مقادیر
  نامعتبر را به پیش‌فرض برمی‌گرداند، `pagingToQuery` نام `size` را به `pageSize` نگاشت
  می‌کند و `pagingToQueryParams` پیش‌فرض‌ها را حذف می‌کند.
- **تغییر فیلتر صفحه را ۱ می‌کند.** فیلتری که نتیجه را کوچک می‌کند نباید کاربر را در
  صفحهٔ ۵ رهاشده نگه دارد.
- **کلیک دوباره روی صفحهٔ فعلی درخواست نمی‌سازد.** `pagingEqual` جلوی ناوبری تکراری را
  می‌گیرد (tc 7).
- **ستون غیرقابل‌سورت دکمه ندارد.** `sortBy` هم با `isSortField` محافظت شده؛ حتی فراخوانی
  مستقیم آن با `categoryName` هیچ تغییری نمی‌دهد (tc 10).
- **`aria-sort` روی `<th>` و `aria-current="page"` روی دکمهٔ فعال** قرار می‌گیرد، نه روی
  یک `<span>` تزئینی.

- **`product-paging.ts` is the only translator.** Invalid values fall back, `size` maps to
  `pageSize`, and defaults are omitted from the URL.
- **A filter change resets page 1**, so a narrower result set cannot leave the user on a
  page that no longer exists.
- **Clicking the active page is a no-op** (`pagingEqual`), and a non-sortable column has no
  button and is rejected by `isSortField`.
- **`aria-sort` sits on the `<th>` and `aria-current="page"` on the active button.**

## اکشن‌های ردیف / Row actions (BO-F06)

هر ردیف سه اکشن دارد: ویرایش (لینک واقعی به `/products/:id/edit`)، تغییر وضعیت و حذف.
در دسکتاپ هر سه به‌صورت inline هستند؛ در موبایل داخل یک منوی سه‌نقطه جمع می‌شوند.
منو **یک نمونهٔ مشترک** است و با `appendTo="body"` رندر می‌شود، بنابراین
`overflow-x-auto` جدول آن را نمی‌برد (tc 10).

Each row exposes edit (a real link), status toggle and delete. On desktop they are inline; on
a phone they collapse into one kebab menu. The menu is a single shared instance appended to
`<body>`, so the table's `overflow-x-auto` cannot clip it (tc 10).

### تغییر وضعیت / Status toggle

1. کلیک روی «وضعیت» → `ConfirmService.confirm({ message: 'محصول «…» غیرفعال شود؟' })`.
2. لغو → هیچ state و درخواستی تغییر نمی‌کند (tc 3).
3. تأیید → `statusOverrides` همان id را به وضعیت جدید نگاشت می‌کند؛ pill **فوراً** عوض
   می‌شود، قبل از پاسخ HTTP (tc 2، tc 7).
4. موفقیت → toast موفقیت، `reload$` و در نتیجه fetch دوباره؛ `reconcileOptimistic`
   overlay را وقتی سرور همان وضعیت را برگرداند پاک می‌کند (tc 6).
5. خطا → overlay پاک می‌شود و pill به مقدار سرور برمی‌گردد (rollback، tc 7). toast خطا
   کار `error-interceptor` است؛ کامپوننت دوباره toast نمی‌زند تا دو پیام تکراری نشود (tc 5).

### حذف / Delete

1. کلیک روی «حذف» → `confirm({ …, danger: true })`؛ دکمهٔ تأیید قرمز است (tc 4).
2. تأیید → id به `removedIds` می‌رود؛ ردیف فوراً از جدول حذف و `total` یکی کم می‌شود.
3. موفقیت → toast و fetch دوباره؛ `reconcileOptimistic` id را وقتی ردیف از پاسخ سرور
   غایب باشد پاک می‌کند.
4. خطا → id از مجموعه حذف و ردیف/تعداد کل برمی‌گردد (rollback).

### مجوز / Permission

اکشن‌ها با `PERMISSIONS` و کلید `products.view` کنترل می‌شوند. بدون این مجوز، هم
اکشن‌های inline و هم منوی موبایل رندر نمی‌شوند و متدهای handler هم no-op هستند (tc 9).
تقسیم دقیق‌تر به `products.edit` / `products.delete` به BO-D07/D08 موکول است.

- Actions are gated by the `products.view` grant; without it neither the inline controls nor
  the mobile menu render, and the handlers are no-ops (tc 9). Finer `products.edit` /
  `products.delete` grants belong to BO-D07/D08.
- The optimistic overlays live above `page().items`, so the server response stays the source
  of truth and a failed request is a clean rollback.

## فرم ایجاد محصول / Create form (BO-F07)

مسیر `/products/new` یک فرم چهارتبی است: **اطلاعات اصلی**، **واریانت‌ها**، **گالری تصاویر**
و **موجودی**. هر چهار تب روی **یک `FormGroup` مرکزی** کار می‌کنند؛ جابه‌جایی تب فقط
`activeTab` را عوض می‌کند و مقدارها را جابه‌جا نمی‌کند. `variants` و `images` از همین حالا
`FormArray` هستند تا BO-F10/F11 فقط ردیف‌ها را اضافه کنند.

The `/products/new` route is a four-tab form: main info, variants, gallery and inventory. All
four tabs share one `FormGroup`; switching only changes `activeTab`, so no value is lost. The
`variants` and `images` arrays exist now so BO-F10/F11 only add rows.

### رفتارها / Behaviour

- **نام → slug:** تابع خالص `slugify` در `product-slug.ts` نام فارسی/لاتین را به slug
  انگلیسی تبدیل می‌کند (`لپ‌تاپ ایسوس` → `laptop-asus`). ویرایش دستی slug، sync را متوقف
  می‌کند. یکتایی و پیشنهاد جایگزین در BO-F16 می‌آید.
- **اعتبارسنجی تب:** `next()` و کلیک روی تب بعدی فقط کنترل‌های همان تب را بررسی و
  `markAsTouched` می‌کنند؛ تب ناقص باز می‌ماند (tc 4). اعتبارسنجی کامل در BO-F08.
- **خروج:** `unsavedProductChangesGuard` روی route نشسته و اگر `form.dirty` باشد با
  `ConfirmService` می‌پرسد. رفرش/بستن مرورگر با `beforeunload` پوشش داده می‌شود (tc 7).
- **ذخیره:** BO-F13 هنوز POST را ندارد؛ دکمه همهٔ کنترل‌ها را touched می‌کند و اگر فرم
  معتبر باشد پیام «در BO-F13 فعال می‌شود» می‌دهد.
- **تب‌های بعدی:** واریانت‌ها (F10) و گالری (F11) ویرایشگر واقعی دارند؛ موجودی (F12) از همین
  حالا `stock` و `lowStockThreshold` را ویرایش می‌کند.

- **Name → slug:** the pure `slugify` in `product-slug.ts` maps Persian/Latin names to an

- **Tab validation:** `next()` validates only the current tab's controls and marks them touched;

## اعتبارسنجی فرم / Form validation (BO-F08)

قواعد اعتبارسنجی در `product-create/product-validators.ts` هستند؛ توابعی خالص که بدون
`TestBed` تست می‌شوند. فرم همان `FormGroup` مرکزی F07 را نگه می‌دارد و فقط ولیدیتورها
عوض شده‌اند.

The rules live in `product-create/product-validators.ts` as pure functions; the central
`FormGroup` from F07 is unchanged apart from its validators.

| فیلد            | قاعده                                           | پیام                                         |
| --------------- | ----------------------------------------------- | -------------------------------------------- |
| نام             | required، trim، ۳–۲۰۰                           | «نام محصول الزامی است.» / «حداقل ۳ کاراکتر…» |
| slug            | required، `[a-z0-9]` با خط تیرهٔ تکی، حداکثر ۸۰ | «فقط حروف انگلیسی، عدد و خط تیره…»           |
| دسته            | required                                        | «دسته‌بندی را انتخاب کنید.»                  |
| قیمت            | required، عددی، بزرگ‌تر از صفر                  | «قیمت باید بزرگ‌تر از صفر باشد.»             |
| موجودی / آستانه | required، عددی، نامنفی                          | «مقدار نمی‌تواند منفی باشد.»                 |
| توضیح کوتاه     | اختیاری، حداکثر ۱۶۰ code point                  | «حداکثر ۱۶۰ کاراکتر مجاز است.»               |

### رفتارها / Behaviour

- **خطا فقط بعد از touched.** `fieldError` اگر کنترل touched نباشد `null` برمی‌گرداند؛ فرم
  دست‌نخورده دیوار قرمز نیست (tc 9). `next()` کنترل‌های تب فعلی را touched می‌کند تا خطاها
  دیده شوند.
- **اصلاح خودکار.** هر تغییر مقدار، ولیدیتورها را دوباره اجرا می‌کند و پیام را برمی‌دارد
  (tc 10).
- **خطای سرور.** `applyServerErrors({ slug: ['این نامک تکراری است.'] })` کلید `server` را روی
  کنترل می‌گذارد و `fieldError` آن را بالاتر از خطای محلی نشان می‌دهد (tc 7). BO-F13 همین
  متد را با `ApiError.fields` صدا می‌زند.
- **پیام‌ها یک‌جا.** قالب هیچ‌جا `control.errors` را نمی‌خواند؛ فقط `errorFor('field')` را
  صدا می‌زند. تغییر متن خطاها یعنی تغییر `REQUIRED_MESSAGE`/`fieldError`، نه جست‌وجو در HTML.

- **Errors only after touch.** `fieldError` returns `null` for an untouched control, so a fresh
  form is not a wall of red (tc 9). `next()` touches the current tab's controls.
- **Auto-correction.** Editing a value re-runs the validators and removes the message (tc 10).
- **Server errors.** `applyServerErrors({ slug: […] })` sets the `server` key and `fieldError`
  prefers it over a local key (tc 7); BO-F13 will feed it `ApiError.fields`.
- **Messages live in one place.** The template calls `errorFor('field')`; it never reads
  `control.errors`.

## سلکت دسته/برند / Category and brand selects (BO-F09)

هر دو سلکت فرم ایجاد حالا `p-select` هستند: **جستجوی محلی**، حالت لودینگ، پیام خطای فارسی
با «تلاش دوباره»، و در موبایل تمام‌عرض. گزینه‌های دسته از `ProductLookupsService` می‌آیند
که در سطح root کش می‌شود؛ ورود دوباره به فرم دو درخواست تازه نمی‌سازد.

Both selects are PrimeNG `p-select`: local search, a loading state, a Persian failure message
with retry, and full width on a phone. Category options come from the root-scoped
`ProductLookupsService`, so revisiting the form does not refetch two lists.

### دسته‌ها / Categories

`buildCategoryOptions` از lookup تخت، مسیر کامل و سطح می‌سازد:

```
{ id: '1', name: 'لوازم برقی', parentId: null }
{ id: '2', name: 'صوتی', parentId: '1' }
→ { path: 'لوازم برقی', level: 0 }
→ { path: 'لوازم برقی / صوتی', level: 1 }
```

- گزینهٔ غیرفعال (`isActive === false`) در `buildCategoryOptions` و در `ProductsService`
  حذف می‌شود (tc 10).
- والد حذف‌شده باعث نمی‌شود مسیر `undefined / نام` شود؛ گزینه به root تبدیل می‌شود.
- `filterBy="path"` جستجو را روی همان مسیر کامل انجام می‌دهد، بدون درخواست اضافه (tc 2).
- item template با `level * 12px` تورفتگی می‌دهد؛ ظاهر درختی بدون ساختار `p-tree`.

### برندها / Brands

- `filterBy="name"` جستجوی محلی روی نام برند.
- item/selected template اگر `logo` داشته باشد تصویر کوچک ۲۰px و در غیر این صورت دایرهٔ
  حرف اول را نشان می‌دهد (tc 3).
- `[showClear]="false"` و یک option واقعی «بدون برند» با `id: ''`؛ کنترل non-nullable می‌ماند و
  مقدار پاک نمی‌شود.

### حالت‌ها / States

- **لودینگ:** `[loading]="categoriesLoading()"` روی خود select؛ بقیهٔ فرم قابل استفاده است

- **خطا:** پیام «بارگذاری دسته‌بندی‌ها ناموفق بود.» + دکمهٔ «تلاش دوباره» که فقط همان
  درخواست را دوباره می‌فرستد (tc 9).
- **پیش‌پرکردن:** `formControlName` با `optionValue="id"`؛ وقتی گزینه‌ها بعد از مقدار برسند،

## ویرایشگر واریانت / Variant editor (BO-F10)

تب «واریانت‌ها» اکنون یک ویرایشگر کامل است: هر ردیف یک `FormGroup` مستقل با SKU، قیمت، موجودی،

## گالری تصاویر / Gallery uploader (BO-F11)

تب «گالری تصاویر» همان کارت «تصاویر محصول» قالب آرینو است: دو ناحیهٔ آپلود — **تصویر اصلی** و
**تصاویر گالری** — که هر دو در یک `FormArray` می‌ریزند. تا وقتی محصول ذخیره نشده، فایل‌ها فقط در
مرورگر می‌زیند؛ هر ردیف به یک `blob:` object URL اشاره می‌کند و `File` (احتمالاً فشرده‌شده) را
برای آپلود BO-F13 نگه می‌دارد.

The gallery tab is the Arino card's «تصاویر محصول»: two dropzones — the cover and the gallery —
feeding one `FormArray`. Until the product is saved the files exist only in the browser; each row
points at a `blob:` object URL and keeps its (possibly compressed) `File` for BO-F13 to upload.

### رفتارها / Behaviour

- **قواعد فایل از خود آرینو آمده‌اند:** PNG، JPG یا GIF، حداکثر ۲ مگابایت و ۵ تصویر؛
  `MAX_IMAGES` و `MAX_IMAGE_SIZE` یک‌جا تعریف شده‌اند. فایل غیرتصویری یا بزرگ‌تر از حد، ردیف
  نمی‌سازد؛ جملهٔ خطا در کادر inline زیر dropzone می‌ماند تا تلاش بعدی آن را برطرف کند.
- **تصویر شاخص یک پرچم است، نه یک جایگاه:** جابه‌جایی ترتیب، کاور را عوض نمی‌کند. حذف کاور،
  اولین تصویر بعدی را ارتقا می‌دهد تا «گالری با ردیف اما بدون کاور» ممکن نشود.
- **چیدمان با drag در دسکتاپ و دکمه در همه‌جا:** `moveImage` تابعی خالص و محافظت‌شده است؛
  drag فقط لایه‌ای نازک روی همان تابع است و کشیدنِ متن انتخابی inputهای alt، کارت را نمی‌کشد.
- **فشرده‌سازی best-effort است:** فایل‌های بالای ۱ مگابایت در ۱۹۲۰px و JPEG با کیفیت ۰٫۸۲
  دوباره encode می‌شوند و هر مسیر شکست، فایل اصلی را برمی‌گرداند. GIF مستثنی است، چون canvas فقط
  فریم اول را می‌کشد و انیمیشن بی‌صدا از بین می‌رفت.
- **حذف بدون تأیید است:** برخلاف ردیف واریانت که دادهٔ تایپ‌شده دارد، یک تصویر با یک کلیک
  دوباره اضافه می‌شود و دیالوگ، اصطکاک بی‌دلیل است.
- **آزادسازی حافظه دو نقطه دارد:** حذف یا تعویض ردیف، و نابودی صفحهٔ `ProductCreate` — نه
  سوییچ تب، که uploader را از بین می‌برد اما آرایه را زنده نگه می‌دارد.

<a href="?path=/story/features-products-gallery--default" target="_top">
  مشاهدهٔ گالری تصاویر در Storybook
</a>

- **File rules come from Arino:** PNG/JPG/GIF, 2 MB and 5 images, exported once (`MAX_IMAGES`,
  `MAX_IMAGE_SIZE`). A rejected file never becomes a row; its sentence stays in the inline error
  box until the next attempt replaces it.
- **The cover is a flag, not a position:** reordering never changes the cover, and deleting it
  promotes the first survivor — a coverless gallery is unreachable.
- **Drag on desktop, buttons everywhere:** `moveImage` is pure and bounds-checked; drag is a thin
  wrapper that ignores text selections inside the alt inputs.
- **Compression is best-effort:** files over 1 MB are re-encoded at 1920px / JPEG-0.82 and every
  failure path returns the original. GIF is exempt because canvas keeps one frame.
- **Delete asks no confirmation** — unlike a typed variant row, an image is one click to re-add.
- **Object URLs are freed in two places:** row remove/replace, and the create page's destroy —
  never the tab switch, which destroys the uploader but keeps the array.

## موجودی و آستانهٔ هشدار / Stock fields (BO-F12)

جدول محصولات و تب «موجودی» فرم هر دو یک سؤال را می‌پرسند: «این کالا چقدر دارد و آیا کم است؟»
پاسخ در `product-stock.ts` است — یک تابع خالص `stockLevel(stock, lowStockThreshold)` با سه خروجی
`out` / `low` / `ok` و یک جدول برچسب/رنگ (`STOCK_LEVEL_META`) که هر دو سطح از آن می‌خوانند.

The products table and the create form's inventory tab ask the same question — how much is
left, and is that low? The answer lives in `product-stock.ts`: one pure
`stockLevel(stock, lowStockThreshold)` returning `out` / `low` / `ok`, plus one label/colour table
(`STOCK_LEVEL_META`) that both surfaces read.

### قواعد / The rules

- **صفر «ناموجود» است، نه «کم‌موجودی».** صفر یعنی قفسه خالی است؛ `0 < stock ≤ threshold` یعنی
  دارد تمام می‌شود. دو جملهٔ متفاوت، دو رنگ متفاوت.
- **آستانه برای هر محصول است، نه یک عدد سراسری.** دو ردیف با موجودی ۸ می‌توانند یکی هشدار بگیرد و
  دیگری نه؛ برای همین آستانه در خودِ ردیف لیست برمی‌گردد.
- **آستانهٔ صفر یعنی «تا وقتی تمام نشده هشدار نده»** — و همین رفتار از فرمول بیرون می‌آید، بدون
  شرط اضافه.
- **موجودی کل از واریانت‌ها می‌آید.** به‌محض وجود یک ردیف واریانت، `syncInventory()` مجموع را در
  کنترل `stock` می‌نویسد (بدون emit، تا حلقه نشود) و ورودی دستی قفل می‌شود. حذف آخرین ردیف،
  فیلد را با همان مقدار به کاربر برمی‌گرداند.

- **Zero is «ناموجود», not «کم‌موجودی».** Zero means the shelf is empty; `0 < stock ≤ threshold`
  means it is running out — two sentences, two colours.
- **The threshold is per product.** Two rows at stock 8 can disagree, which is why the number
  travels in the list row instead of being one constant on the page.
- **A threshold of 0 means "warn only when empty"**, and that falls out of the formula with no
  extra branch.
- **The total comes from the variants.** Once a variant row exists, `syncInventory()` writes their
  sum into `stock` (without emitting, so it cannot loop) and the manual field locks. Deleting the
  last row hands the field back with the same value.

### تریس یک نمونه / One worked trace

فرم ایجاد: نام «هدفون سونی»، دو واریانت با موجودی ۴ و ۶، آستانه ۵.

1. `variants.push(...)` → `updateValueAndValidity()` روی آرایه → `form.valueChanges`.
2. اشتراک سازندهٔ `ProductCreate` → `syncInventory()`.
3. `derived = true`؛ `sumVariantStock` = ۱۰؛ `stock` کنترل با `emitEvent: false` روی ۱۰؛
   `inventory = { total: 10, threshold: 5, derived: true }`.
4. `inventoryLevel = stockLevel(10, 5) = 'ok'` → بج «موجود».
5. تب موجودی: ورودی read-only با ۱۰، «منبع موجودی: واریانت‌ها»، خلاصه = ۱۰.

## ارسال محصول / Submitting the form (BO-F13)

دکمهٔ «ذخیره محصول» (هم در هدر و هم در فوتر ویزارد) فرم را اعتبارسنجی می‌کند، بدنه را با

The «ذخیره محصول» button (header and wizard footer) validates the form, builds the body with
`toCreateProductDto(form)`, and sends `POST /products`. Until the answer arrives both buttons show
a spinner through `pLoading` and become **natively disabled** — a keyboard user cannot create two
products.

| 201             | `saved` ست می‌شود (گارد دیگر سؤال نمی‌پرسد)، toast موفقیت، و انتقال به `/products/{id}/edit` (tc 1/2) |
| 422 با `fields` | هر پیام روی کنترل خودش می‌نشیند و تبِ همان فیلد باز می‌شود؛ هیچ داده‌ای پاک نمی‌شود (tc 3/7)          |
| خطای شبکه/500   | اینترسپتور پیام را نشان داده؛ فرم بنر «تلاش دوباره» می‌گیرد و مقادیر دست‌نخورده می‌مانند (tc 5)       |

- **بنر فقط برای خطای غیرفیلدی است.** خطای ۴۲۲ عمداً toast نمی‌شود (اینترسپتور
  `isValidation` را رد می‌کند) تا پیام یک‌بار و کنار همان input دیده شود.
- **`server` خطا با ارسال دوباره پاک می‌شود.** `clearServerErrors()` قبل از هر `save()` کلید
  `server` را از کنترل‌ها برمی‌دارد، وگرنه کنترلِ نامعتبر جلوی درخواست بعدی را می‌گرفت و کاربر
  در بن‌بست می‌ماند (tc 7).
- **گالری با `blob:` ارسال نمی‌شود.** آدرس object URL فقط داخل همان تب معتبر است؛ `images`
  تنها URLهای واقعی را می‌فرستد و بایت‌ها از مسیر `imageFiles()` به endpoint آپلود می‌رسند.

## ویرایش محصول / Editing a product (BO-F14)

`/products/:id/edit` همان فرم ساخت است، نه یک نسخهٔ دوم. مسیر با یک `resolve` محصول کامل را
(با واریانت‌ها، گالری و آستانه) قبل از اولین رندر می‌آورد و `withComponentInputBinding()` آن را به
`input` صفحه می‌دهد؛ پس کاربر هیچ‌وقت فرم خالی نمی‌بیند که بعد پر شود.

`/products/:id/edit` is the create form, not a second copy. The route resolves the full product —
variants, gallery and threshold included — before the first paint, and
`withComponentInputBinding()` hands it to the page's `edit` input, so the user never sees an empty
form that fills in later.

### سه ورودی، سه رفتار / Three inputs, three behaviours

| ورودی `edit`         | نتیجه                                                                                          |
| -------------------- | ---------------------------------------------------------------------------------------------- |
| `null` (مسیر `/new`) | فرم خالی؛ ذخیره `POST` می‌کند و به صفحهٔ ویرایش می‌رود (F13)                                   |
| `{ product }`        | هر چهار تب پیش‌پر می‌شوند؛ ذخیره `PUT /products/:id` می‌زند و در همان صفحه می‌ماند (tc 1‑4، 7) |
| `{ error }`          | فرم رندر نمی‌شود؛ کادر خطا با «تلاش دوباره» می‌آید (tc 6)                                      |

- **۱۶۰/۴۰۴ با `RedirectCommand`:** اگر `GET /products/:id` ۴۰۴ بدهد، resolver به‌جای برگرداندن
  داده، `RedirectCommand('/404')` می‌دهد؛ ناوبری لغو و صفحهٔ ۴۰۴ می‌آید (tc 5).
- **نامک دست‌نخورده می‌ماند:** پیش از hydrate، `slugEdited` ست می‌شود؛ وگرنه تغییر نام محصول،
  نشانی (URL) ذخیره‌شده را عوض می‌کرد.
- **ذخیره بدون تغییر خطا نمی‌دهد:** بعد از `PUT`، فرم `markAsPristine` می‌شود و `hasChanges` صفر؛
  همان مقادیر خط پایهٔ جدید هستند (tc 10) و گارد خروج دیگر سؤال نمی‌پرسد.
- **«تلاش دوباره» دو تنظیم لازم دارد:** `onSameUrlNavigation: 'reload'` در دکمه و
  `runGuardsAndResolvers: 'always'` روی مسیر؛ بدون هر دو، دکمه بی‌صدا هیچ کاری نمی‌کند.

## حذف محصول / Deleting a product (BO-F15)

حذف نرم است: رکورد در سمت سرور می‌ماند اما هیچ خوانشی آن را برنمی‌گرداند. در پنل، دکمهٔ «حذف»
همان دیالوگ قرمز را باز می‌کند (BO-F06) و حالا تعداد واریانت‌ها را هم می‌گوید: حذف محصول،
واریانت‌هایش را هم از فروش خارج می‌کند.

Deleting is soft: the record stays on the server and every read hides it. In the panel, «حذف» opens
the same red dialog as BO-F06 and now names the variant count — deleting a product takes its
variants off sale with it.

- **تعداد از خودِ ردیف می‌آید.** `variantsCount` روی `ProductListItem` است، پس دیالوگ بدون
  درخواست اضافه باز می‌شود. صفر یعنی محصول ساده است و جملهٔ ساده‌تری می‌آید، نه «۰ واریانت».
- **لغو، هیچ کاری نمی‌کند.** `confirm` که `false` بدهد، نه overlay، نه درخواست، نه toast (tc 2).
- **ردیف قبل از پاسخ می‌رود.** `removedIds` ردیف را فوری حذف می‌کند و اگر API رد کند برمی‌گردد
  (tc 3/4)؛ toast موفقیت فقط بعد از پاسخ سرور.
- **mock هم حذف نرم را بلد است.** `DELETE` شناسه را در یک `Set` نگه می‌دارد، لیست و جزئیات آن را
  از آن به بعد برنمی‌گردانند و `resetMockDeleted()` برای تست‌ها آن را پاک می‌کند (tc 8).
- **بازیابی ادمین طراحی نشده** و در این تسک انجام نشد (tc 9 مشروط است)، چون ستون/فیلتر
  «حذف‌شده‌ها» در قرارداد API نیست.
